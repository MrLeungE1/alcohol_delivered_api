## 二、接入 AI 前必须先完成的事情

### 1. 完成订单业务闭环

至少需要有：

- 创建订单
- 支付成功/失败
- 取消订单
- 配送中
- 已完成
- 退款/售后
- 库存扣减及恢复
- 订单金额由服务端计算
- 订单状态变更记录

当前 [orders.py](D:/Project/fastapiPro/alcohol_delivered_api/app/models/orders.py) 只有总金额、用户、地址和简单状态，不足以进行完整的销售分析。

建议以后补充：

- `pay_status`
- `paid_at`
- `cancelled_at`
- `completed_at`
- `refund_amount`
- `discount_amount`
- `delivery_fee`
- `payment_amount`
- `payment_method`
- `order_source`
- `activity_id`
- `updated_at`

订单明细还应保存下单时的商品快照：

- 商品分类
- 原价、实际售价
- 下单时成本价
- 优惠金额
- 活动信息
- 商品规格

否则商品之后改价、改分类，会污染历史销售报表。

### 2. 建立可靠的用户身份体系

目前多个接口直接接收前端传来的 `user_id`，这既不安全，也会造成用户行为数据不可信。

管理端登录目前还是明文密码和固定 token：

- [sys_admin.py](D:/Project/fastapiPro/alcohol_delivered_api/app/services/admin/sys_admin.py)

需要先完成：

- 微信登录/openid 换取用户身份
- JWT 或服务端会话
- 从 token 中获取当前用户
- 管理员权限和普通用户权限隔离
- 密码哈希
- AI 管理接口权限控制

### 3. 金额必须由后端计算

当前购物车接口允许前端传入 `price` 和 `total_price`：

- [cart.py](D:/Project/fastapiPro/alcohol_delivered_api/app/services/wx/cart.py)

这些数据不能直接作为销售分析依据。后续应由后端根据商品价格、活动、优惠规则重新计算，否则用户可以篡改金额，AI 分析出来的利润和销售额也会失真。

### 4. 增加用户行为埋点

订单只能告诉你“最终买了什么”，无法告诉你“为什么没买”。

建议增加统一的 `user_event` 行为表，记录：

- 商品曝光
- 商品点击
- 查看详情
- 搜索关键词
- 加入购物车
- 修改购物车
- 删除购物车
- 提交订单
- 支付成功
- 收藏/分享
- 推荐位曝光和点击

推荐系统尤其需要记录：

```text
user_id
event_type
product_id
activity_id
scene
session_id
request_id
event_time
metadata
```

其中 `request_id` 能把“推荐曝光 → 点击 → 加购 → 下单”串联起来，方便评估推荐效果。

## 三、AI 销售分析应该怎么做

销售分析不应让大模型直接读取数据库后自由计算。

推荐采用两层结构：

```text
数据库/数据仓库
      ↓
SQL 指标计算层
      ↓
结构化销售指标
      ↓
大模型解释、总结、生成建议
```

数字计算交给 SQL，大模型负责：

- 总结趋势
- 解释异常
- 生成日报、周报
- 发现值得关注的商品
- 给出活动和库存建议

第一阶段可以支持这些指标：

- 销售额、实付金额
- 订单量、客单价
- 销量、毛利、毛利率
- 商品/分类销售排行
- 新老用户销售占比
- 复购率
- 退款率
- 加购转化率
- 活动销售效果
- 库存周转
- 滞销商品
- 时段、区域销售分布

典型管理端 Agent 问题：

- “总结昨天的销售情况。”
- “最近七天哪些商品销量下降明显？”
- “哪些商品销量高但利润低？”
- “下周哪些商品可能缺货？”
- “端午节活动中哪些商品表现最好？”

建议第一版只允许 Agent 调用预先定义好的分析工具，例如：

- `get_sales_summary`
- `get_product_ranking`
- `get_inventory_risk`
- `get_activity_performance`
- `get_customer_retention`

不要第一版就允许模型生成并执行任意 SQL。

## 四、AI 推荐可以分三阶段

### 阶段一：规则推荐

不需要训练模型，优先落地：

- 热销商品
- 新品
- 同分类商品
- 高毛利商品
- 活动商品
- 购物车搭配商品
- 库存充足商品
- 用户历史购买分类

最终推荐分可以类似：

```text
热度 + 用户偏好 + 活动权重 + 毛利权重 + 库存权重
```

这比单纯使用现在的 `is_hot` 字段更灵活。

### 阶段二：个性化推荐

数据量积累后，可以加入：

- 基于商品属性的内容推荐
- “购买了 A 的用户也购买了 B”
- 用户偏好分类
- 价格区间偏好
- 品牌、酒类、容量、度数偏好
- 复购周期推荐

因此商品模型还需要逐渐丰富属性：

- 品牌
- 酒水类型
- 酒精度
- 容量
- 产地
- 口味
- 适用场景
- 包装规格
- 标签

### 阶段三：排序模型

当有足够曝光、点击、加购、购买数据后，再训练排序模型，预测：

- 点击概率
- 加购概率
- 购买概率
- 预期销售额或利润

大模型不适合直接承担商品排序模型，它更适合做“理解用户自然语言需求”和“解释推荐理由”。

## 五、Agent 建议拆成两类

### 管理端销售 Agent

面向运营人员：

- 查询销售指标
- 生成经营日报
- 库存预警
- 活动复盘
- 商品运营建议
- 自然语言查询数据

第一版建议只读，不允许自动改价格、上下架或创建活动。涉及写操作时，应生成操作建议，由管理员确认。

### 用户端导购 Agent

面向小程序用户：

- 根据预算推荐
- 根据聚会、送礼、佐餐等场景推荐
- 解释商品差异
- 推荐搭配
- 查询库存、配送范围
- 从对话直接生成候选购物车

用户端 Agent 必须经过业务过滤：

```text
模型候选结果
→ 商品存在
→ 已上架
→ 有库存
→ 在配送范围
→ 符合年龄与业务限制
→ 返回用户
```

不能把大模型生成的商品名称、价格或库存直接返回。

## 六、建议增加的模块

未来可以按下面方式组织，但现在不用急着创建：

```text
app/
  ai/
    providers/        大模型供应商适配
    prompts/          Prompt 模板
    tools/            Agent 可调用工具
    agents/           销售 Agent、导购 Agent
    recommend/        推荐召回与排序
    analytics/        指标查询
    evaluations/      AI 效果评估
  models/
    user_event.py
    recommendation_log.py
    ai_conversation.py
    ai_task.py
```

基础设施方面可能需要：

- 大模型 API
- Redis：缓存、对话状态、异步任务
- Celery/RQ/其他任务队列：日报、批量分析
- 定时任务
- 日志与监控
- Prompt 和模型版本管理

向量数据库暂时不是必需品。只有在商品说明、运营文档、酒类知识很多，需要语义检索时再引入。

## 七、AI 特有的安全要求

酒水业务尤其需要注意：

- 年龄限制和未成年人保护
- 不根据敏感信息进行不当用户画像
- 不鼓励过量饮酒
- 用户地址、手机号不能直接发送给模型
- 模型不能直接执行任意数据库写操作
- AI 输出需要保留调用记录
- 记录模型、Prompt、工具参数和结果
- 设置超时、重试、限流和预算上限

## 八、推荐实施顺序

最合理的路线是：

1. 完成登录、订单、支付状态、库存事务。
2. 修正金额计算和权限安全问题。
3. 增加用户行为埋点。
4. 建立销售指标查询接口。
5. 先做管理端销售看板和规则推荐。
6. 接入大模型，让它解释指标并生成经营报告。
7. 增加只读销售 Agent。
8. 数据积累后做个性化推荐。
9. 最后考虑可执行操作的 Agent，并加入人工确认。

一句话概括：先把项目建设成“数据可信的电商系统”，再把 AI 放在指标解释、自然语言交互和推荐排序上。现阶段最值得优先投入的是订单闭环、埋点和指标体系，而不是先选哪个大模型。
